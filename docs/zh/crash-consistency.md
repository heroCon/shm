# 崩溃一致性

保证：附在某个 topic 上的进程在数据路径的任意指令被杀死后，其余进程能把 topic 修到每块要么空闲、要么被合法引用，然后继续收发。数据路径无锁。修复由调用它的进程按需执行。

不保证：死亡进程正在发布或取走的那条消息，对私有订阅者和至多一次的组会丢失。至少一次的组会把成员已声明或正持有的消息放回组队列；这一步中间崩溃可能投递两次，这是该策略允许的。超过 `max_deliveries` 则计入 `dead_lettered` 并丢弃。

## 机制

每块有一个 64 位字：低 56 位是持有者位图，高 8 位是队列引用计数。贷款表在设置位之前记下 id，清除位之后忘掉它，所以回收一个槽只碰它自己的表项。`take()` 用一次 `fetch_add` 把队列引用换成持有者位。

每个端点用 OFD 锁占着自己的槽字节，进程死亡时内核释放该锁。组的成员关系是位图，加入和离开各是一次原子操作。

活动字是 `{counter, op, block}`。空的 `take()` 不写它，这样空转的读者不会挡住 `recover()`。

## 修复

`collect_garbage()` 不需要整个 topic 静止。它先等每个正处于操作中的活端点走出这一步（上限 100 ms），然后：

- 仍被预留、未提交的单元写成墓碑；
- 已声明未释放的单元被释放；若某个已死槽的持有者位说明调用者已经转换过，就保留队列引用；
- 重算死亡发布者正在投递的那一块，并用 CAS 写回；
- 至少一次的组里，死亡成员持有的块先放回组队列，再清持有者位。

超时则槽保持 `RECLAIMING`，下次继续。无法归属的泄漏会置 `repair_pending`，下一次 `collect_garbage()` 或耗尽的 `loan()` 会跑 `recover()` 并清掉该标志。

`recover()` 仍需要一次静止窗口：锁住维护字节和每个能锁的槽，读活动字，扫描，再读一次；看到非空闲或变化就返回 `kBusy`。然后按快照用 CAS 重算块字、填墓碑、释放单元、清钉住掩码和过期成员位。

## 故障矩阵

`crash_matrix_test` 在 `SHM_PUBSUB_FAULT_INJECTION` 下编译。`SHM_PUBSUB_CRASH_AT=name:N` 让进程在该点第 N 次命中时收到 `SIGKILL`。普通构建里这个宏是空的。每个点都测命中 1、2、3、5，以及只调用 `collect_garbage()` 的一轮。`local_repair_test` 在其他端点继续运行时杀死一个端点。`chaos_test` 持续杀死发布者，并限制每个读者的最长停顿。

## 仍然存在的窗口

- `recover()` 需要活端点都不在操作中间。持续流量会让它返回 `kBusy`。有了本地修复和 self-heal 之后，死发布者留下的空洞不会把读者永久堵住。
- 空闲列表的 pop/push 各由一次 CAS 提交。结构损坏时 `recover()` 返回 `kCorrupted`，应重建区域。
- 入队之后、唤醒之前被杀死，读者要等到下一次发布、`stop()` 或超时。
- 空闲列表的 ABA 标记和活动计数器是 32 位。
